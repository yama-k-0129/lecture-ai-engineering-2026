## 演習

- 第1回（素のLLM）とエージェントの回答の違い：同じ質問「3レベルとは？」に対し、第1回の `app.ask`（素のLLM、用語集なし）は「AIE2026は想定」「通常は」と断りつつ、レベル1〜3（初級・中級・応用）という一般的な3段階を推測で説明し、正確な内容は宿題の案内資料や講師に確認するよう勧めた。正解は基礎・実装・発展で、どれか1つで完了、原則採点なしなので、推測の中身は合っていない（レベル2を「標準・中級」としたり、全員必須・選択のルールを挙げた）。エージェントは先に `search_glossary` を呼び、用語集どおりの内容と末尾の「第1回」を示せた。代わりにコストは増える：素のLLMは入力21トークン・LLM 1回・応答3.12秒、エージェントは入力1399トークン（ツール定義・用語集の検索結果が加わる）・LLM 2回。
- `--trace` で見えたツール呼び出し（ツール名と引数）：「3レベル」は `search_glossary({'query': '3レベル'})` の1回。「LoRAとQLoRAの違いは？」は `search_glossary({'query': 'LoRA'})` と `search_glossary({'query': 'QLoRA'})` の2回（用語を1つずつ）。「第2回の内容から確認問題を1問出して」は `make_quiz({'lecture': 2})`（出題は「学習率」）。
- 1つの質問での LLM 呼び出し回数（`requests`）：3問とも 2（ツール呼び出しの回 + 最終回答の回）。「LoRAとQLoRA」は検索が2回でも requests は 2（2つの検索が同じ回にまとめて依頼される）。tool_calls は 1・2・1。
- 追加したツールと、docstring に書いた説明：`make_quiz(lecture: int)`。「指定した回の用語集から確認問題を1問作り、問題と答えを返す。出題を頼まれたときに使う。answer は利用者が答えたあとの採点・解説に使う（先に見せない）」。用語が無い回（`make_quiz(0)`）は、用意されている回の一覧を返す。`--list-tools` に表示されること、`pytest` が通ることを確認した。`--trace` で `make_quiz({'lecture': 2})` が呼ばれることを確認した。

## 宿題

- 取り組んだレベル：基礎・実装・発展(a) 
- やったこと：`app/` は書き換えず、`scripts/lec03_basic_experiment.py` で変更版のエージェントを作り、1回に1か所だけ変えて、各条件を3回ずつ実行した（モデル gemini-3.5-flash-lite）。
  - E1：INSTRUCTIONS から「必ず search_glossary で用語集を確認する」の行を削除
  - E2：`search_glossary` の docstring「1つだけ入れる」→「まとめて入れる」
  - E3：INSTRUCTIONS の「最後に第N回を示す」→「最後に確認問題を1問出す」
- 結果：
  - E1：変化なし。検索の行を消しても、2つの質問とも3回とも E0（基準）と同じ回数・引数で検索した。
  - E2：「LoRAとQLoRA」の検索が、`LoRA`・`QLoRA` の2回から、`'LoRA QLoRA'` の1回に変わった（3/3）。ただし requests はどちらも2のまま。
  - E3：「第N回」の表示が消え（3/3）、代わりに確認問題が付いた（3/3）。
- 気づき・疑問：
  - ツール呼び出しは3回とも同一で、揺れたのは文章だけだった。条件が同じでも出力は揺れるので、1回だけの比較は当てにならない。
  - docstring の一語（「1つだけ」→「まとめて」）で、引数と検索回数が変わった。ツールの説明文は仕様書であり、プロンプトの一部でもある。
  - 検索結果を使っても、用語集に無い一般知識（「通常は16ビット」など）が混ざった。「推測で断定しない」の指示だけでは、補足的な知識は止まらない。
  - 回答の正誤は、用語集と見比べて目で判断したもの。自動採点ではない。
- 実装（`save_learning_log`）：`requires_approval=True` で登録し、`output_type=[str, DeferredToolRequests]`、承認結果と `message_history` を渡して再実行するループを書いた。実際の LLM で承認(y)と拒否(n)を試した（`impl_results.md`）。
  - 承認：実行が承認待ちで止まり、y で `learning_log/` に Markdown が1つできた。拒否：ファイルはできず、`ToolDenied` の理由文を受けたモデルは「拒否されたので保存しなかった」と答えた。
  - 承認の時点で利用者が見るのは、モデルが依頼文から整えたタイトルと本文。保存前に内容を確認できる点に価値がある。
  - 承認をはさむと LLM 呼び出しは2回になるが、再開後の `result.usage.requests` は1としか出ない（実行ごとに数える）。
- 発展(a) ADK で書き直した結果：`adk_agent/glossary_agent/agent.py` に、`app/agent.py` の `INSTRUCTIONS` と `app/tools.py` のツール3つ（`search_glossary`・`get_lecture_summary`・`make_quiz`）をそのまま渡して `adk run` で動かし、演習と同じ3問を投げた。
  - 書き方の違い：Pydantic AI は `Agent(instructions=…)` に `agent.tool_plain(fn)` を1つずつ登録し、モデルは実行時に渡す。ADK は `Agent(instruction=…, tools=[fn, …], model="gemini-…")` を一度に書き、モデル名を固定する。ツールは普通の関数をそのまま渡せる点は同じ。
  - 使い勝手の違い：`adk run` は対話が続き、質問のたびにコマンドを打たなくてよいが、デフォルトではツール呼び出しが画面に出ない。Pydantic AI の自作 CLI は `--trace` でツール名・引数・戻り値・`requests`・コストまで見られるが、質問ごとにコマンドを打つ。pythonプログラムで開発することを前提とした場合、開発中の確認には後者、できあがったエージェントを動かすには前者が向くと感じた。
  - 気づき：`INSTRUCTIONS` に `save_learning_log` の行があるのに ADK 版にはそのツールを渡さなかったところ、モデルは存在しないツールを、本来ない `lecture` 引数付きで呼んだ。実行はされず（エラーの中身までは確認していない）、モデルは「保存ツールが使えない」と答えた。指示とツール一覧は食い違わないように保つ必要がある。
